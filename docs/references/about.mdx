# About Net F/T

Net F/T is a community-maintained open-source organization for integrating ATI Ethernet force/torque sensors into applications, automation, and robotics. It is not affiliated with or endorsed by ATI Industrial Automation.

## Repository responsibilities

| Repository     | Responsibility                                                                      |
| -------------- | ----------------------------------------------------------------------------------- |
| `netft-cpp`    | Standalone C++ protocol, configuration, sample, health, and recovery SDK            |
| `pyNetFT`      | Typed synchronous Python bindings and compatibility migration                       |
| `netft-cli`    | Terminal commissioning, checking, monitoring, recording, and bias                   |
| `netft-viewer` | Cross-platform desktop visualization and CSV recording                              |
| `ros-netft`    | ROS standalone driver and `ros2_control` sensor hardware                            |
| `netft-docs`   | Canonical user journeys, tutorials, shared concepts, reference, and troubleshooting |

Component repositories own source, releases, migration notes, maintainer procedures, and implementation details. This site owns complete user-facing workflows and stable public interface references, with mechanical API facts extracted from pinned component releases.

## Contributing documentation

Verify software claims against current code, configuration, tests, or release metadata. Verify hardware claims against current official ATI documentation. Do not infer support from one CI job or copy volatile README prose without checking the implementation.

Tests should protect metadata contracts, routes, links, executable examples, and builds. They must not freeze wording, headings, disclaimers, or source formatting. Public examples may use ATI's documented factory-default address but must not contain laboratory addresses, credentials, recordings, or private network details.

See the repository `CONTRIBUTING.md` for the local pnpm workflow and pull-request checklist. ## Maintenance and issue routing

The organization has seven repositories: five runtime components, `netft-docs`, and `.github`. The component inventory and supported distribution metadata are maintained in `data/ecosystem.json`; each component owns its source, release checks and version-specific support contract.

| Concern                                          | Owning repository |
| ------------------------------------------------ | ----------------- |
| RDT protocol, calibration, native recovery       | `netft-cpp`       |
| Python delivery and compatibility API            | `pyNetFT`         |
| Terminal parsing, diagnostics, recording         | `netft-cli`       |
| ROS nodes, controllers, distribution integration | `ros-netft`       |
| Desktop interaction, companion, packaging        | `netft-viewer`    |
| Shared user guides and source references         | `netft-docs`      |
| Organization navigation and policies             | `.github`         |

Fix shared core behavior upstream, then verify each consumer's pinned source manifest and adaptations. The compatibility page uses the maintained component inventory; consult the ROS repository for the exact distribution contract and validation gaps. Candidate documentation explicitly identifies unreleased behavior.
